# Bug Report: Fibonacci AI Coding Agent VS Code Extension

## Overview

This is a comprehensive bug audit of the Fibonacci AI Coding Agent, a VS Code sidebar extension providing an autonomous AI coding agent. The project has ~46 source files across extension host (TypeScript/Node.js) and webview (React/TypeScript).

---

## CRITICAL BUGS (P0) — Data loss, hangs, or security

### 1. Dangling approval promise causes agent loop hang
**File:** `src/core/approvalManager.ts:72-76`, `src/core/agentLoop.ts:638-647`
**Impact:** Agent loop hangs forever

The `requestApproval()` method returns a `Promise` that only resolves when the webview posts back an `APPROVE` message. If the user closes VS Code, closes the webview, or the extension deactivates while an approval is pending, the promise never resolves. The agent loop at line 639 `await`s this promise, causing the entire agent to hang indefinitely.

**Root cause:** No timeout or abort-awareness in the promise resolution path. The `AbortController` signal is checked at lines 145 and 379 but NOT between lines 639-647 where the approval blocks.

**Fix:** Add a race between the approval promise and the abort signal:
```typescript
const approval = await Promise.race([
  this.deps.approvals.requestApproval({...}),
  new Promise<ApprovalResponse>((resolve) => {
    this.abortController.signal.addEventListener('abort', () => resolve({ id: '', approved: false, reason: 'cancelled' }), { once: true });
  }),
]);
```

### 2. Revert failures silently swallowed — rejected code persists on disk
**File:** `src/core/agentLoop.ts:647, 711, 1481`
**Impact:** Code the user rejected may be saved to disk

Three instances of `.catch(() => {})` on `revertPreview()`:
- Line 647: User rejects a file write → revert silently fails → rejected code stays in editor → autoSave writes it to disk
- Line 711: Commit to disk fails → revert silently fails → partial write may persist
- Line 1481: Fallback file creation revert fails → orphaned file on disk

**Fix:** At minimum, log the error. Better: show a warning notification to the user that revert failed and they should manually verify the file.

### 3. `web_fetch` tool has no SSRF protection
**File:** `src/tools/webTools.ts:59-127`
**Impact:** Internal network access via prompt injection

The `web_fetch` tool accepts arbitrary URLs and makes HTTP requests. While it validates the URL starts with `http://` or `https://`, there is no restriction on internal/private IP ranges. A malicious prompt injection could instruct the AI to fetch:
- `http://169.254.169.254/latest/meta-data/` (AWS metadata)
- `http://localhost:*` (local services)
- Internal corporate URLs

**Fix:** Add IP range validation to block private/link-local addresses (10.x, 172.16-31.x, 192.168.x, 127.x, 169.254.x, ::1, etc.).

### 4. `process.cwd()` fallback writes to wrong directory on Windows
**File:** `src/tools/memoryTools.ts:39`
**Impact:** Memory data written to VS Code installation directory

```typescript
const home = process.env.HOME || process.env.USERPROFILE || process.cwd();
```

If both `HOME` and `USERPROFILE` are undefined, `process.cwd()` is used. On Windows, this could point to the VS Code installation directory rather than the user's home, causing memory data to be written in an unexpected location.

**Fix:** Remove the `process.cwd()` fallback entirely; throw an error if neither env var is set, or use a known safe path like `os.homedir()`.

## HIGH BUGS (P1) — Reliability, correctness

### 5. `deactivate()` doesn't clean up MCP servers
**File:** `src/extension.ts:397-399`
**Impact:** Orphaned child processes after extension deactivation

```typescript
export function deactivate(): void {
  // Nothing to clean up
}
```

MCP servers are spawned as child processes but never killed on deactivation. `McpManager.disconnectAll()` is never called. Over time this can accumulate zombie processes.

**Fix:** Call `mcpManager.disconnectAll()` in `deactivate()`.

### 6. `as any` private member access in MCP tools
**File:** `src/tools/mcpTools.ts:270-272`
**Impact:** Fragile coupling, silent breakage

```typescript
const session = (manager as any).sessions.get(String(args.server));
const resp = await (manager as any).rpc(session, 'resources/list', {});
```

Accesses private `sessions` map and private `rpc` method directly. If the internal structure changes, this breaks silently at runtime with no compile-time error.

**Fix:** Add public `getRawSession()` and `callRawRpc()` methods to `McpManager`, or implement `get_mcp_resources` inside the `McpManager` class.

### 7. MCP RPC timeout timer never cleared on success
**File:** `src/tools/mcpTools.ts:178-183`
**Impact:** Timer reference leak, stale timer fires

Every RPC call creates a 30-second `setTimeout` that is never cleared when the RPC succeeds. While the stale rejection is a no-op (promise already resolved), the timer reference prevents GC until it fires.

**Fix:** Store the timeout ID and clear it in the resolve/reject paths.

### 8. Default API endpoint uses HTTP (not HTTPS)
**File:** `src/api/fibonacciClient.ts:22`, `src/extension.ts:457`
**Impact:** API keys transmitted in plaintext

```typescript
this.baseURL = cfg.get<string>('baseURL') ?? 'http://my.fibonacci.monster/api/v1';
```

The default endpoint URL uses HTTP, meaning API keys sent in headers are transmitted in cleartext. Any network observer can intercept them.

**Fix:** Change default to `https://my.fibonacci.monster/api/v1`.

### 9. `fire-and-forget` void calls lose errors
**File:** `src/core/agentLoop.ts:193, 204`, `src/tools/executeCodeTools.ts:240`

```typescript
void liveCoder.processDelta(delta, rawBuffer);       // line 193
void liveCoder.processOpenAIDelta(...);               // line 204
void handleToolCall(req);                             // line 240
```

These `void` calls discard the returned promise. If the async function throws after the initial synchronous portion, the error becomes an unhandled rejection.

**Fix:** For `processDelta`/`processOpenAIDelta`, wrap in try/catch. For `handleToolCall`, add `.catch(err => console.error(...))`.

### 10. `runningTerminals` map never cleaned up
**File:** `src/tools/terminalTools.ts:24`
**Impact:** Accumulated stale references

Terminals are added to the map when `run_in_terminal` is called but never removed, even after the terminal is disposed by the user.

## MEDIUM BUGS (P2) — Code quality, maintainability

### 11. Debug `console.log` statements left in production code
**Files:** `src/webviewProvider.ts:189, 202, 221`, `src/extension.ts:41, 55, 110`

Six `console.log('[fibonacci-agent] ...')` statements in production code. These pollute the output channel and should use `console.debug()` or be gated behind a debug flag.

### 12. Code duplication: `getCurrentWorkspaceRoot()` duplicated 5+ times
**Files:** `fileTools.ts:22`, `searchTools.ts:55`, `codeEditTools.ts:21`, `editorTools.ts:125`, `liveCoder.ts:152`, `filePreview.ts:58`, `extension.ts:32`

The same workspace root resolution logic is copy-pasted across 7 files. A bug fix or behavior change must be made in all 7 places.

### 13. Inconsistent `err.message` null guards
**Files:** `webTools.ts:125`, `searchTools.ts:297, 344`, `codeEditTools.ts:164`

Some catch blocks guard against undefined `err.message` (e.g., `fibonacciClient.ts:95-97`), but others use the naive pattern `err instanceof Error ? err.message : String(err)` which can produce `"undefined"` if `err.message` is undefined.

### 14. `replace_in_file` only replaces first occurrence
**File:** `src/tools/fileTools.ts:239`

Uses `indexOf()` which only finds the first match. If the model intends to replace multiple occurrences, only the first is replaced. This could lead to subtle bugs where the model thinks it replaced all instances.

### 15. Regex with user input could cause ReDoS
**File:** `src/tools/searchTools.ts:201-202`

```typescript
regex = new RegExp(pattern, caseInsensitive ? 'gi' : 'g');
```

User-supplied regex patterns are compiled without sanitization. Malicious patterns like `(a+)+$` can cause catastrophic backtracking. The 30s timeout mitigates but doesn't prevent the hang.

## LOW BUGS (P3) — Hygiene, minor issues

### 16. Deprecated `npm-run-all` dependency
**File:** `package.json`
Replace with `npm-run-all2` (actively maintained).

### 17. Unused dependencies: `@types/mocha`, `@modelcontextprotocol/sdk`
**File:** `package.json`
`@types/mocha` — no mocha in the project. `@modelcontextprotocol/sdk` — MCP client is custom-built.

### 18. Runtime dependencies listed as `devDependencies`
**File:** `package.json`
`openai`, `diff`, `zustand`, `react`, `react-dom` are runtime dependencies bundled into output. Should be in `dependencies` per npm convention (though bundling makes it functionally equivalent).

### 19. Broken `test` script
**File:** `package.json`
`"test": "node ./dist/test/runTest.js"` — this file doesn't exist. Tests are in `scripts/test-hermes.ts` and `scripts/test-detectors.ts`.

### 20. `activationEvents: ["onStartupFinished"]` activates on every VS Code start
**File:** `package.json`
This is the broadest activation event. Since the extension registers a sidebar view, `"onView:fibonacci.agentView"` alone would be more efficient for lazy loading.

### 21. Dead code: `void subRegistry` in delegate tools
**File:** `src/tools/delegateTaskTools.ts:170`

### 22. `onModelChangedCallbacks` array grows without bounds
**File:** `src/webviewProvider.ts:407`
Callbacks are added but never removed.

### 23. `.gitignore` doesn't exclude `.kilo/`, `.mimocode/`, `mimo.exe`
The 123MB `mimo.exe` binary and `.kilo/` with its own `node_modules/` are committed to the repo.

### 24. `mimo.exe` (123MB) in git repository
A large binary checked into version control bloats the repo.

### 25. Missing Prettier/EditorConfig
No formatting consistency enforcement across the project.

### 26. ESLint 8 is EOL
Will block future upgrades. ESLint 9 uses flat config format.

### 27. `compileGlob` doesn't handle brace expansion
**File:** `src/tools/searchTools.ts:365-393`
`{*.ts,*.js}` patterns won't work.

### 28. `as any` disables type safety project-wide
**File:** `.eslintrc.js`
`@typescript-eslint/no-explicit-any: 'off'` weakens the type system.

## VERIFICATION PLAN

For each fix, test by:
1. **P0 #1 (hang):** Start an agent task, approve a file write, then close the webview mid-approval. Verify the agent doesn't hang.
2. **P0 #2 (revert):** Simulate a revert failure (e.g., corrupt file handle) and verify the user sees a warning.
3. **P0 #3 (SSRF):** Try `web_fetch` with `http://169.254.169.254/` and verify it's blocked.
4. **P0 #4 (cwd):** Unset HOME and USERPROFILE, trigger memory write, verify correct path.
5. **P1 #5 (deactivate):** Connect an MCP server, deactivate extension, verify no orphaned processes.
6. **P1 #8 (HTTPS):** Reset base URL to default, verify it's HTTPS.
7. **P1 #9 (void):** Introduce a deliberate async error in `processDelta`, verify it's caught.
8. **P1 #10 (terminals):** Run 10 `run_in_terminal` calls, dispose terminals, check map size.
9. **All:** Run `npm run lint` and `npm run check-types` to verify no new type errors.
